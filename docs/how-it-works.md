# Як влаштований каталог

Один скрипт, один файл винятків, один workflow. Усе інше — згенероване.

```
README.md                      ← генерується, не редагувати руками
data/forks.json                ← генерується: знімок даних, дає осмислений git-діф
scripts/update.py              ← правила категорій + збір + рендеринг
scripts/overrides.json         ← єдине місце для ручних правок
update.ps1                     ← локальний запуск
.github/workflows/weekly.yml   ← cron щопонеділка + ручний запуск
```

## Конвеєр

1. **Збір.** GraphQL-запит до GitHub повертає всі форки разом із даними оригіналу
   (`parent`): опис, зірки, ліцензія, дата останнього коміту, теми. REST-ендпоінт
   `/users/{user}/repos` поля `parent` не має — без нього форк лишається просто
   назвою без контексту, тому GraphQL тут не оптимізація, а необхідність.
2. **Класифікація.** Кожен репозиторій отримує рівно одну категорію.
3. **Рендеринг.** `README.md` і `data/forks.json` перезаписуються цілком.

Сторінка запиту — 50 вузлів. Це не випадкове число: зі 100 вузлами та вкладеним
`parent` GitHub відповідає `HTTP 502`, бо запит перевищує ліміт вартості. Плюс
чотири спроби з експоненційною паузою, бо на пікових навантаженнях 502 трапляється
й на валідних запитах, а тижнева задача не має падати через це.

## Як працює класифікатор

### Нормалізація

Текст (назва + опис + теми свої й оригіналу) перетворюється на рядок виду
`" токен токен токен "`. Ключове слово шукається теж обрамленим пробілами.

Це дає межі слів безкоштовно. Наївний пошук підрядка `"ai" in text` знаходить
`ai` всередині `email`, `training` і `Ukraine` — і половина колекції осідає в
«AI-агентах» без жодних підстав.

Перед нормалізацією розбивається CamelCase: `MachineLearningRoadmap` →
`machine learning roadmap`. Без цього злиті назви репозиторіїв не дають жодного
збігу.

**Відома межа.** Розбиття орієнтується на перехід «мала → велика літера», тож
`PlayWrightProject` стає `play wright project` — і слово `playwright` не
знаходиться. Такі випадки видно одразу: вони потрапляють у «Нерозібране» і
лікуються одним рядком у `overrides.json`. Це свідомий вибір: додавати другий
режим зіставлення заради двох репозиторіїв дорожче, ніж дописати виняток.

### Порядок правил

Перемагає **перший** збіг, тому порядок категорій у `CATEGORIES` — це і є основна
логіка. Вузьке стоїть перед широким:

| Пара | Чому саме так |
| --- | --- |
| безпека → QA | «penetration **testing**» інакше потрапляє в тестування |
| QA → агенти | `explorbot` описує себе як «AI Agent for Exploratory Browser **Testing**» |
| LLM-інфра → пам'ять | у `vllm` слово `memory` означає RAM: «**memory**-efficient serving engine» |
| медіа → агенти | сьогодні кожен конвертер зветься AI-інструментом: «An **AI**-boost downloader» |

Якщо додаєте категорію — думайте не про ключові слова, а про те, **між якими**
наявними категоріями її поставити.

### Формат ≠ тема

Awesome-списки не мають власної категорії. Список про безпеку лежить у безпеці з
міткою 📋. Інакше єдине спільне між `awesome-agent-skills` і
`awesome-bugbounty-tools` — формат — визначало б структуру каталогу.

Мітки нараховуються окремо від категорії:

| Мітка | Умова |
| --- | --- |
| 📋 | назва починається з `awesome`, або в описі є «curated list» / «a list of» / «collection of» |
| ⚠️ | оригінал або форк заархівовано |
| 💤 | оригінал без комітів понад `STALE_DAYS` (за замовчуванням 365) |
| 🗑️ | оригінал видалено або недоступний |

Мітки 💤 і ⚠️ — головна практична користь щотижневого запуску: видно, що з
колекції протухло, не відкриваючи 279 сторінок.

## Ручні правки

`scripts/overrides.json` — єдиний файл, який редагується руками:

```json
{
  "назва-форку": {
    "category": "ключ-категорії",
    "note": "коротка нотатка, потрапляє в таблицю жирним"
  }
}
```

Обидва поля необовʼязкові. Тільки `note` — залишити автоматичну категорію, але
додати пояснення. Тільки `category` — мовчки перекласти на іншу полицю.

Доступні ключі: `archive`, `security`, `qa`, `skills`, `llm-infra`, `memory`,
`media`, `agents`, `devops`, `resources`, `web`, `other`.

**Коли правити правила, а коли — винятки.** Один-два репозиторії — виняток.
Якщо ж «Нерозібране» росте або цілий клас проєктів систематично сідає не туди —
це діагноз правилам, і лікувати треба порядок категорій чи ключові слова.

## Перевірка

```bash
python scripts/update.py --self-test
```

Мережу не чіпає. Перевіряє межі слів, розбиття CamelCase, опорні точки
класифікації (`nuclei`→безпека, `explorbot`→QA, `awesome-agent-skills`→skills),
пріоритет винятків над правилами, нарахування міток і екранування таблиці.

Тест запускається першим кроком у workflow: якщо порядок категорій зламали,
каталог не перегенерується зіпсованим.

## Запуск

**Автоматично.** `.github/workflows/weekly.yml`, щопонеділка о 06:00 UTC. Коміт
робиться лише коли змінився `data/forks.json` — README містить дату генерації й
відрізнявся б щоразу, засмічуючи історію порожніми комітами.

**Вручну на GitHub.** Actions → «Оновлення каталогу» → Run workflow.

**Локально.**

```powershell
.\update.ps1          # тільки перегенерувати
.\update.ps1 -Push    # перегенерувати й запушити, якщо є зміни
```

Щотижневе завдання Windows, якщо потрібне саме локальне розклад:

```powershell
schtasks /create /tn "forks-atlas" /sc weekly /d MON /st 09:00 `
  /tr "powershell -NoProfile -File `"$PWD\update.ps1`" -Push"
```

## Токен

Береться в такому порядку: `GITHUB_TOKEN` → `GH_TOKEN` → `gh auth token`.

У Actions підставляється вбудований `secrets.GITHUB_TOKEN` — окремий PAT не
потрібен, бо читаються лише публічні дані, а запис іде в цей самий репозиторій.
Якщо колись знадобиться враховувати приватні форки, доведеться завести PAT з
областю `repo` і покласти його в секрет із тим самим імʼям.
